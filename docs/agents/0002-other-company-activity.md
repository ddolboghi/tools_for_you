# PRD: 타사 활동·특이사항 항목 개편

## 배경

상권 보고문의 3, 4번 항목은 지금 수영과 부산대 두 상권에서만 나옵니다. 3번은 켈리·대선·새로라는 **주류** 이름 아래 인원 수 하나와 자유 텍스트 하나를 받고, 4번은 자사 판촉물 재고량을 박스 단위로 받습니다.

현장에서 필요한 것은 다른 것입니다. 3번은 주류가 아니라 **회사**별로, 인원을 대판팀과 행사팀으로 나눠서 세야 합니다. 자유 텍스트로 받던 판촉물·판촉내용은 실제로 쓰이지 않습니다. 4번의 자사 판촉물 재고량은 더 이상 보고 대상이 아니고, 그 자리에는 다른 항목에 담기지 않는 일을 적을 특이사항이 와야 합니다.

그리고 이 두 항목은 상권을 가리지 않고 항상 나와야 합니다. 지금의 상권별 분기(`additionalInfoBusinessZones`)는 그 자체가 제거 대상입니다.

이 개편은 Supabase에 영향이 없습니다. `action/report.ts`는 상권, 방문업소 수, 계산 결과, 근무자, 전환, 추가주문만 저장하고 3, 4번 항목은 원래 저장하지 않습니다.

## 용어

[CONTEXT.md](../../CONTEXT.md)의 용어를 따릅니다. 이번에 추가된 용어는 타사 활동, 대판팀, 행사팀, 특이사항입니다.

## 요구사항

### R1. 3, 4번을 모든 상권에 항상 표시

- MUST: 3, 4번 항목의 입력 UI와 보고문 출력이 선택한 상권과 무관하게 항상 나온다.
- MUST: `utils/sale/businessZones.ts`의 `additionalInfoBusinessZones` 상수를 삭제한다. 이 상수를 읽던 세 곳(`utils/sale/report.ts`, `components/sale/SaleCalculation.tsx`, `components/sale/Result.tsx`)의 조건 분기도 함께 없앤다.
- 근거: 상권마다 다르게 보고하던 것을 통일하는 것이 이번 변경의 핵심이다. 분기를 없애면 그 상수는 아무도 읽지 않는 죽은 코드가 된다.

### R2. 3번 항목을 타사 활동으로 교체

- MUST: 대상은 하이트진로, 대선주조, 롯데주류 세 회사로 고정한다. 이 순서를 지킨다.
- MUST: 회사마다 대판팀 인원과 행사팀 인원을 각각 숫자로 입력받는다.
- MUST: 근무자가 회사를 추가하거나 삭제하는 기능은 없다.
- MUST: 판촉물·판촉내용 자유 텍스트 입력을 없앤다. 지금 기본값으로 들어 있는 문구("스푸너, 모닝케어, 아이셔, 비타500 젤리 일반 판촉 행사" 등)도 함께 사라진다.
- MUST: 보고문 출력은 아래와 정확히 같다. 항목 줄은 들여쓰기 없이 `- `로 시작한다.

```
3. 타사 활동
- 하이트진로: 대판팀 0명 / 행사팀 0명
- 대선주조: 대판팀 0명 / 행사팀 0명
- 롯데주류: 대판팀 0명 / 행사팀 0명
```

- MUST: 입력이 비어 있으면 `0`으로 출력한다.
- 근거: 타사 인력 현황이 실제로 보고에 필요한 정보이고, 자유 텍스트 항목은 쓰이지 않는다.

### R3. 4번 항목을 특이사항으로 교체

- MUST: 자사 판촉물 재고량 입력 기능을 전부 제거한다. `utils/sale/promotionStock.ts`, `components/sale/promotionStock/PromotionStockInput.tsx`, `components/sale/report/PromotionStockReport.tsx`, `utils/sale/types.ts`의 `PromotionStock` 타입을 삭제한다.
- MUST: 특이사항은 한 줄짜리 텍스트 입력 칸 하나로 받는다. 여러 줄 입력이나 항목 추가는 없다.
- MUST: 입력값의 앞뒤 공백을 제거한 결과가 비어 있으면 `없음`을 출력한다.
- MUST: 보고문 출력은 아래와 정확히 같다. 4번 본문은 항상 한 줄이다.

```
4. 특이사항
- 없음
```

- 근거: 재고량은 더 이상 보고 대상이 아니다. 특이사항은 짧은 메모라 한 줄이면 충분하고, 칸이 하나면 출력 형태가 항상 한 줄로 정해져 보고문이 예측 가능하다.

### R4. 이름 규칙

- MUST: 타입은 `OtherCompanyActivity`로, 필드는 `name`, `daepanTeam`, `haengsaTeam`으로 한다. 인원 필드의 타입은 `number | undefined`다.
- MUST: 초기값 상수는 `utils/sale/otherCompanyActivity.ts`의 `initOtherCompanyActivities`로 한다. 기존 `utils/sale/otherCompanyPromotion.ts`는 남기지 않는다.
- MUST: 컴포넌트는 `components/sale/otherCompanyActivity/OtherCompanyActivity.tsx`와 같은 디렉터리의 `OtherCompanyActivityInput.tsx`, 보고 표시용은 `components/sale/report/OtherCompanyActivityReport.tsx`로 한다. 기존 `components/sale/otherCompanyPromotion/` 디렉터리는 남기지 않는다.
- MUST: 특이사항은 별도 컴포넌트 파일을 만들지 않고 `SaleCalculation.tsx`와 `Result.tsx`에 직접 넣는다.
- 근거: 글로서리의 용어가 판촉인원에서 타사 활동으로 바뀌었으므로 코드의 이름도 따라가야 한다. 대판팀·행사팀은 대응하는 영어 단어가 없어 로마자로 적으며, 이는 `galmegi`, `bsky` 같은 이 레포의 기존 방식과 같다. 한 줄 입력 칸 하나에 파일을 새로 만드는 것은 과하다.

### R5. 1, 2번 출력 불변

- MUST: 보고문의 1번과 2번 부분은 이번 변경 전후로 글자 단위로 동일해야 한다.
- MUST: 2번 마지막 줄과 `3. 타사 활동` 사이에는 빈 줄이 하나 있다. 3번 마지막 줄과 `4. 특이사항` 사이에도 빈 줄이 하나 있다.
- 근거: 이번 요청은 3, 4번에 한정된다. 앞부분이 바뀌면 보고를 받는 쪽이 먼저 알아챈다.

### R6. 모바일 레이아웃

- MUST: 3번 입력 행이 폭 390px 화면에서 잘리거나 가로 스크롤을 만들지 않는다. 회사 이름과 숫자 칸 두 개가 한 줄에 다 들어가지 않으면 두 줄로 나눈다.
- MUST: 4번 입력 칸도 같은 조건을 만족한다.
- 근거: 주 사용 환경이 모바일이고, 이 화면은 최근에 같은 종류의 잘림 문제를 고쳤다. 회사 이름 네 글자에 "대판팀", 숫자 칸, "명", "/", "행사팀", 숫자 칸, "명"까지 한 줄에 넣으면 여유가 거의 없다.

## 범위 밖

- **Supabase 스키마 변경과 저장 항목 추가.** 3, 4번은 원래 저장되지 않으며, 이번에도 저장하지 않는다.
- **1, 2번 항목의 내용 변경.** R5 참조.
- **담당자 보고문(`getSMReport`).** 3, 4번 항목이 없는 별개의 보고문이다.
- **자사 판촉물 재고량의 다른 형태로의 부활.** 이번에는 완전히 제거한다.
- **푸시와 병합.** 작업은 `other-company-activity` 브랜치의 워크트리에서 하고 태스크마다 커밋한다. 원격 반영과 `main` 병합은 사용자가 결정한다.

- [ ] 상권을 무엇으로 바꿔도 복사되는 보고문에 3, 4번이 들어 있다
- [ ] 3번 입력란에 하이트진로, 대선주조, 롯데주류가 이 순서로 있고 각각 숫자 칸이 두 개다
- [ ] 3번 입력란에 자유 텍스트 칸이 없다
- [ ] 아무것도 입력하지 않은 보고문의 3번이 PRD의 예시와 글자 단위로 같다
- [ ] 대판팀에 2, 행사팀에 3을 넣으면 해당 줄이 `- 하이트진로: 대판팀 2명 / 행사팀 3명`이 된다
- [ ] 4번 입력 칸이 한 줄짜리 텍스트 칸 하나다
- [ ] 특이사항을 비워 두면 보고문에 `- 없음`이 나온다

- [ ] 폭 390px에서 3, 4번 입력 영역에 가로 스크롤이나 화면 밖 요소가 없다
- [ ] `additionalInfoBusinessZones`가 코드베이스에 없다
- [ ] `PromotionStock`, `initPromotionStocks`, `PromotionStockInput`, `PromotionStockReport`가 코드베이스에 없다
- [ ] `otherCompanyPromotion`이라는 이름의 파일과 디렉터리가 코드베이스에 없다

## 검증

`npm install` 후 더미 값이 든 `.env.local`을 만들고 `npm run build`를 통과해야 합니다.

`utils/getSupabaseClient.ts`가 모듈 로드 시점에 `createClient`를 호출하므로, 환경변수가 없으면 코드와 무관하게 빌드가 실패합니다. `.env.local`은 gitignore 대상이라 레포에 남지 않고 실제 Supabase에도 연결되지 않습니다.

테스트는 없습니다. 출력 비교 항목은 변경 전후 보고문 문자열을 직접 비교해 확인하고, 390px 레이아웃 항목은 개발 서버를 띄운 뒤 브라우저 폭을 390px로 두고 화면 밖으로 나간 요소가 있는지 재서 확인합니다.
