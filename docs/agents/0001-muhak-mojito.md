# PRD: 무학 모히또 집계 항목 추가

## 배경

좋은데이 판촉 근무자는 야간 판촉 후 상권별 음용비를 집계하고, 상권 톡방과 담당자에게 각각 보고문을 보냅니다. 무학의 주류로 모히또가 추가되었으나 도구가 이를 집계하지 못합니다.

현재 구조에서 데이터 프레임(`data/sale/report.ts`)에 주류를 더하면 입력 폼, 화면 결과, 백분율 계산은 자동으로 따라옵니다. 그러나 클립보드로 복사되는 보고문 두 개는 주류명이 한 줄씩 하드코딩되어 있어 반영되지 않습니다.

이것이 단순 누락으로 끝나지 않는 이유는 상권 보고문의 회사 합계가 데이터에서 계산되기 때문입니다. 데이터에만 모히또를 추가하면 무학 합계는 모히또를 포함하는데 아래 항목 목록에는 나오지 않아, 합계와 항목의 합이 어긋난 보고문이 조용히 나갑니다.

전환·추가주문은 점유비와 별개 구조입니다. 회사 개념이 없고 칸이 숫자 인덱스로 고정되어 있으며, 칸 목록("좋은데이 / 부산갈매기 / 톡톡")이 열 군데에 중복으로 적혀 있습니다.

## 요구사항

### R1. 모히또를 점유비 집계 항목으로 추가

- MUST: 데이터 프레임의 `"가. 무학"` 아래에 모히또를 추가한다.
- MUST: 모히또는 무학 안에서 좋은데이 바로 다음 자리에 온다. 즉 좋은데이, 모히또, 톡시리즈, 부산갈매기 순이다.
- MUST: 모히또는 좋은데이나 톡시리즈에 합산되지 않는 독립 항목이다.
- 근거: 무학이 모히또 실적을 별도로 집계한다. 순서는 좋은데이 계열끼리 묶어 읽히게 하기 위함이다.

### R2. 상권 보고문을 데이터 순회로 전환

- MUST: `getBSKYReport`의 네 회사 블록을 전부 데이터 프레임 순회로 바꾼다. 어느 회사도 하드코딩으로 남기지 않는다.
- MUST: 모히또를 0으로 둔 상태에서, 모히또 줄을 제외한 나머지 출력이 변경 전과 글자 단위로 동일해야 한다. 회사 사이 빈 줄과 항목 앞 공백 두 칸을 포함한다.
- MUST: 하드코딩된 `마. 기타: 0t (0%)` 줄은 지금 위치에 그대로 유지한다. 이 항목은 데이터 프레임에 없다.
- 근거: 회사 합계는 데이터에서 계산되는데 항목 목록만 하드코딩이라 둘이 어긋날 수 있다. 순회로 바꾸면 그 불일치가 구조적으로 불가능해지고, `data/sale/report.ts`의 "새로운 주류는 이 형태로 추가합니다"라는 주석이 실제로 참이 된다.

### R3. 담당자 보고문의 무학 부분을 데이터 순회로 전환

- MUST: 복사용 텍스트(`getSMReport`)와 화면 컴포넌트(`SMReport`) 양쪽을 함께 바꾼다. 두 곳의 내용이 어긋나면 안 된다.
- MUST: 표시용 이름을 데이터 키와 별도로 두어 기존 문구를 유지한다. 좋은데이는 "좋은데이", 톡시리즈는 "좋은데이 톡시리즈", 부산갈매기는 "갈매기", 모히또는 "모히또"로 표시한다.
- MUST: 타사 항목(대선(C1포함), 진로, 참이슬, 새로, 청하(별빛청하 포함))은 지금의 추려낸 목록과 순서를 그대로 유지한다. 이쪽은 순회로 바꾸지 않는다.
- 근거: 담당자 보고문은 전체 목록이 아니라 "무학 전 주류 + 타사 주요 제품"이라는 큐레이션이다. 무학만 규칙이 명확해 순회가 맞고, 담당자가 읽어온 문구는 바뀌면 안 된다.

### R4. 전환·추가주문에 모히또 칸 추가

- MUST: 칸 이름 목록을 상수 하나로 분리하고, 입력 UI·합계 헤더·화면 결과·보고문 텍스트가 모두 그 상수를 순회한다.
- MUST: 모히또는 마지막 칸이다. 즉 이름, 좋은데이, 부산갈매기, 톡톡, 모히또 순이다.
- MUST: 기존 칸의 숫자 인덱스가 바뀌지 않는다. 좋은데이는 1, 부산갈매기는 2, 톡톡은 3을 유지하고 모히또가 4가 된다.
- MUST: 다섯 칸이 들어가도 입력 행 레이아웃이 깨지지 않는다. 이 화면의 최대 폭은 500px이고 주 사용 환경은 모바일이다.
- MUST: 근무자별 부산갈매기 집계(`getGalmegiSumByWorker`)는 계속 인덱스 2를 읽는다.
- 근거: 이 데이터는 Supabase에 숫자 위치로 저장되므로 중간에 칸을 끼우면 과거 기록과 자리가 어긋난다.

### R5. 톡시리즈와 톡톡의 표기 유지

- MUST: 점유비의 "톡시리즈"와 전환·추가주문의 "톡톡"은 같은 술이지만, 각 맥락의 표기를 그대로 둔다. 어느 쪽으로도 통일하지 않는다.
- 근거: 근무자와 보고 수신자에게 익숙한 문구이고, 이번 요청과 무관한 변화다.

### R6. 죽은 코드 삭제

- MUST: `data/sale/order.ts`의 `initOrder1`을 삭제한다.
- 근거: 어디서도 쓰이지 않는다. 게다가 `initOrder2`가 다섯 칸이 되면서 `initOrder1`의 주석("갈매기19, 갈매기16")과 칸 수가 같아져 혼동을 준다.

### R7. 결정 기록

- MUST: 전환·추가주문에 칸을 추가한 결정을 `docs/adr/`에 ADR로 남긴다.
- MUST: ADR은 저장 형태가 바뀐다는 점, 이미 쌓인 기록에는 다섯 번째 값이 없다는 점, 그럼에도 칸을 넣기로 한 이유를 담는다.
- 근거: 되돌릴 수 없는 결정이다. 나중에 과거 데이터를 분석할 때 경계가 어디인지 알 수 있어야 한다.

## 범위 밖

- **Supabase 스키마 변경.** `calculation_result`와 `orders`가 JSON 컬럼이라 필요 없다.
- **과거 저장 기록의 마이그레이션.** 모히또 이전 기록은 다섯 번째 값이 없는 채로 둔다.
- **푸시와 병합.** 작업은 `muhak-mojito` 브랜치의 워크트리에서 하고 태스크마다 커밋한다. 원격 반영과 `main` 병합은 사용자가 결정한다.
- **톡시리즈와 톡톡의 명칭 통일.** R5 참조.

## 수용 기준

- [ ] 무학 입력란에 모히또 칸이 좋은데이 다음에 나온다
- [ ] 모히또에 숫자를 넣으면 총 테이블 수와 무학 점유비에 반영된다
- [ ] 상권 보고문의 무학 블록에 모히또 줄이 있다
- [ ] 상권 보고문의 무학 합계가 네 항목 값의 합과 일치한다
- [ ] 모히또를 0으로 둔 상권 보고문이 모히또 줄을 빼면 변경 전과 글자 단위로 같다
- [ ] 담당자 보고문에 "좋은데이 톡시리즈"와 "갈매기" 문구가 그대로 남아 있다
- [ ] 담당자 보고문에 모히또 줄이 있다
- [ ] 담당자 보고문의 복사 텍스트와 화면 표시가 같은 항목을 같은 순서로 보여준다
- [ ] 전환·추가주문 입력 행에 다섯 번째 칸이 있고 500px 폭에서 레이아웃이 깨지지 않는다
- [ ] 전환·추가주문의 합계 헤더, 화면 결과, 보고문 텍스트 세 곳 모두에 모히또가 나온다
- [ ] 근무자별 부산갈매기 집계가 모히또 칸 추가 전과 같은 값을 낸다
- [ ] `initOrder1`이 코드베이스에 없다
- [ ] `docs/adr/`에 ADR 파일이 있다

## 검증

`npm install` 후 더미 값이 든 `.env.local`을 만들고 `npm run build`를 통과해야 합니다.

`utils/getSupabaseClient.ts`가 모듈 로드 시점에 `createClient`를 호출하므로, 환경변수가 없으면 코드와 무관하게 빌드가 실패합니다. `.env.local`은 gitignore 대상이라 레포에 남지 않고 실제 Supabase에도 연결되지 않습니다.

테스트는 없습니다. 수용 기준의 출력 비교 항목은 변경 전후 보고문 문자열을 직접 비교해 확인합니다.
